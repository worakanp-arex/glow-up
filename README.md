# glow-up

แพลตฟอร์มสนับสนุนโอกาสการทำงาน การเรียนรู้ และการดูแลตัวเองสำหรับผู้ผ่านการบำบัด

แนวทางหัวข้อหน้า ไอคอน และปุ่มย้อนกลับ: [รูปแบบ UI](frontend/UI_CONVENTIONS.md)

## โครงสร้างและฟีเจอร์

- `frontend/`: React 19 + Vite, UI ภาษาไทย โทนฟ้า รองรับมือถือและโหมดมืด เมนูตามบทบาท และโหลดหน้าแบบ lazy
- `backend/`: Express + MongoDB/Mongoose, JWT ผ่าน HttpOnly cookie, Socket.IO สำหรับแจ้งเตือน
- บทบาท: ผู้ใช้งาน นายจ้าง บุคลากรทางการแพทย์ และผู้ดูแลระบบ
- สมัครสมาชิกด้วย OTP / Google Sign-In, โปรไฟล์ ทักษะ และเอกสาร
- ค้นหางาน สมัครงาน จัดการผู้สมัคร และยืนยันนายจ้าง/ประกาศงาน
- เช็คอินอารมณ์ สถิติต่อเนื่อง แบบประเมินรายสัปดาห์ และนัดปรึกษา
- ชุมชน คอร์ส บทเรียน สถานการณ์ฝึกฝน ภารกิจ และรางวัล
- สมัครสมาชิกประเภทครอบครัว/ผู้ดูแล ผ่าน OTP หรือ Google และรับคำเชิญเพื่อติดตามเฉพาะสรุปความก้าวหน้า

## เริ่มต้น

ใช้ Node.js 22.12 ขึ้นไป และ MongoDB ที่เปิดใช้งานอยู่

```sh
npm ci --prefix backend
npm ci --prefix frontend
```

คัดลอก `backend/.env.example` เป็น `backend/.env` แล้วตั้ง `MONGODB_URI` และ `JWT_SECRET`
คัดลอก `frontend/.env.example` เป็น `frontend/.env` หากต้องใช้ Google Sign-In หรือเปลี่ยน API proxy

เปิดคนละ terminal:

```sh
npm run dev --prefix backend
npm run dev --prefix frontend
```

Backend ใช้พอร์ต **5001**, frontend ใช้ **5173** หากเปลี่ยนพอร์ต backend ให้ตั้ง `API_PROXY_TARGET` ใน frontend ให้ตรงกัน
บน Windows PowerShell ที่บล็อก `npm.ps1` ให้ใช้ `npm.cmd` แทน `npm`

สร้างข้อมูลเริ่มต้นเมื่อจำเป็น:

```sh
npm run seed:admin --prefix backend
npm run seed:missions --prefix backend
npm run seed:skills --prefix backend
```

### ข้อมูลตัวอย่างสำหรับสาธิต

ใช้กับ MongoDB ในเครื่องเท่านั้น (สคริปต์ปฏิเสธการทำงานกับฐานข้อมูลอื่น เพราะรหัสผ่านตัวอย่างเปิดเผยอยู่ใน repo) และ**ไม่แก้ไขหรือลบข้อมูลเดิม**

```sh
npm run seed:demo:full --prefix backend          # สร้าง (หรือสร้างใหม่) ทั้งชุด
npm run seed:demo:people:clean --prefix backend  # ลบเฉพาะผู้ใช้และกิจกรรมตัวอย่าง
npm run seed:demo:full:clean --prefix backend    # ลบทั้งหมด รวมเนื้อหา "[ตัวอย่าง]" (บทเรียน สถานการณ์ โพสต์ ภารกิจครอบครัว)
```

- `seedDemo.js` สร้างเนื้อหา: บทเรียน 17 บท (ผู้ใช้ 12, ครอบครัว 5) สถานการณ์จำลอง 8 ข้อ ภารกิจครอบครัว 8 รายการ โพสต์ตัวอย่าง
- `seedDemoPeople.js` สร้างบัญชีตัวอย่าง 42 บัญชี: ผู้ป่วย 28 คน (ความเสี่ยงสูง 5 / ปานกลาง 8 / ต่ำ 15), ผู้ให้คำปรึกษา 2, นายจ้าง 6 (รอตรวจสอบ 1), ครอบครัว 6
  พร้อมงาน 32 ตำแหน่ง (เปิด ปิด หมดอายุ รอตรวจ ถูกปฏิเสธ) ที่เขียนรายละเอียดแยกเป็น "หน้าที่หลัก / คุณสมบัติและสิ่งที่ต้องทำได้ / สวัสดิการและเงื่อนไข" และไม่ใส่ลิงก์ประกาศต้นฉบับ เพราะบริษัทตัวอย่างเป็นข้อมูลสมมติ ใบสมัครราว 70 รายการครบทุกสถานะ คอร์สจริง 16 รายการ (ลิงก์ชี้ถึงหน้าคอร์สของ Chula MOOC, CU-NEURON, DSD, SET e-Learning และกรมสุขภาพจิต พร้อมวันสิ้นสุดตามเว็บ) บันทึกอารมณ์ 100 วัน ผลประเมินความเสี่ยงย้อนหลัง
  แบบประเมินรายสัปดาห์ เหตุการณ์เสี่ยง นัดปรึกษา ภารกิจและเกม ชุมชน และการแจ้งเตือน ระดับความเสี่ยงคำนวณด้วยสูตรจริงของระบบ จึงตรงกับที่แดชบอร์ดแสดง
- ผู้ป่วยตัวอย่างบางส่วนถูกมอบหมายให้ผู้ให้คำปรึกษาคนแรกที่มีอยู่ในระบบ เพื่อให้ล็อกอินด้วยบัญชีจริงของคุณแล้วเห็นข้อมูลได้
- ทุกบัญชีตัวอย่างใช้รหัสผ่านเดียวกัน `DemoGlow#2026` อีเมลรูปแบบ `patient01`…`patient28`, `employer1`…`employer6`, `counsellor2`–`counsellor3`, `family1`…`family6` ตามด้วย `@demo.glowup.example`
  (โดเมนนี้สงวนไว้ ไม่มีกล่องจดหมายจริง ระบบจึงไม่ส่งอีเมลหาใครโดยบังเอิญ)
- การลบด้วย `seed:demo:full:clean` ลบเนื้อหา "[ตัวอย่าง]" ทั้งหมดรวมถึงบันทึกที่อ้างอิงถึงมันด้วย (ผลทำสถานการณ์จำลอง ภารกิจครอบครัวที่ทำไปแล้ว) หากมีบัญชีทดสอบของคุณเองที่ใช้เนื้อหาเหล่านี้อยู่ ให้ใช้ `seed:demo:people:clean` แทน

ตั้ง `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD` และ `SEED_ADMIN_NAME` ก่อนสร้าง admin
การ seed ภารกิจจะเพิ่มหรืออัปเดตรายการภารกิจและรางวัลในฐานข้อมูลที่ตั้งค่าไว้
การ seed ทักษะอาชีพจะเพิ่มทักษะมาตรฐานที่จัดเป็นหมวด (ไม่แก้ไขหรือลบทักษะที่มีอยู่) และเซิร์ฟเวอร์จะเติมทักษะที่ขาดให้อัตโนมัติทุกครั้งที่เริ่มทำงาน
เซิร์ฟเวอร์ยังส่งการแจ้งเตือนคอร์สที่ใกล้หมดอายุทุกชั่วโมง (รองรับการรันแบบ instance เดียวตามที่ระบุใน `deploy/ecosystem.config.cjs`)

แบนเนอร์บนหน้าคอร์ส (`frontend/src/components/courses/CourseBanner.jsx`) ใช้รูปปกที่เจ้าหน้าที่ตั้งไว้ของแต่ละคอร์ส (ถ้าไม่ตั้งใช้รูปสำรองตัวเดียวกับการ์ด) วางเต็มสัดส่วนชิดขวาโดยไม่ตัดตัวหนังสือในภาพ มีสีเข้มไล่จากซ้ายมาหาข้อความ และเลื่อนวนได้สูงสุด 5 คอร์ส
คอร์สที่เรียนค้างอยู่ขึ้นก่อน ตามด้วยคอร์สที่ `GET /api/courses/featured` เลือกให้: จับคู่จากทักษะของผู้ใช้ (ถ่วงน้ำหนักตามระดับที่ตั้งไว้) แล้วหยิบสลับทักษะละคอร์สเพื่อไม่ให้เต็มไปด้วยเรื่องเดียว ป้ายใต้ชื่อคอร์สบอกเหตุผลตามจริง
`ตรงกับทักษะ` (ชื่อทักษะตรงกับคอร์ส) · `เหมาะกับสายงาน` (จับจากหมวดของทักษะ) · `เพราะคุณบันทึกงาน ...` และถ้ายังไม่ครบจะเติมคอร์สที่เปิดอยู่จากหมวดที่ยังไม่มี หมวด "ทักษะชีวิตและการทำงาน" ไม่ใช้เป็นตัวจับคู่เพราะกว้างเกินไป
แบนเนอร์เลื่อนเองทุก 6.5 วินาที หยุดเมื่อเมาส์อยู่บนแบนเนอร์หรือโฟกัสด้วยคีย์บอร์ด มีปุ่มหยุด/เล่น ปุ่มก่อนหน้า/ถัดไป และรองรับลูกศรซ้าย-ขวากับการปัดบนมือถือ ผู้ที่ตั้งค่าลดการเคลื่อนไหวของระบบจะไม่เลื่อนเอง
ถ้าปกที่เจ้าหน้าที่อัปโหลดเป็นภาพแนวนอน 16:9 จะแสดงได้เต็มที่ที่สุด

## การตั้งค่าและข้อมูลส่วนตัว

- โหลด environment ก่อนสร้างบริการ Google/SMTP; ทุกโหมด**ยกเว้น** `NODE_ENV=development` และ `test` ถือเป็น production: ต้องมี JWT secret สุ่มอย่างน้อย 32 ตัวอักษร (ไม่ใช่ค่าตัวอย่างหรือรูปแบบซ้ำ), `CORS_ORIGIN`, `FRONTEND_URL` และ SMTP การลืมตั้ง `NODE_ENV` จึงไม่ทำให้ระบบหลวมลง — **ตอนพัฒนาในเครื่อง ให้ใส่ `NODE_ENV=development` ใน `backend/.env`**
- การล็อกอินใช้ cookie แบบ HttpOnly อายุเท่ากับ token (ค่าเริ่มต้น 1 วัน ปรับด้วย `JWT_EXPIRES_IN`) token ไม่ถูกส่งกลับใน JSON และถูกยกเลิกทันทีเมื่อเปลี่ยน/รีเซ็ตรหัสผ่าน ระงับ ลบ หรือถอนการยืนยันบัญชี
- รหัสผ่านใหม่ต้องยาว 10–128 ตัวอักษรและไม่ใช่รหัสที่เดาง่าย (รหัสเดิมที่ตั้งไว้ก่อนหน้ายังล็อกอินได้)
- การลบบัญชีเป็นแบบ soft delete: บัญชีหายจากระบบและเข้าสู่ระบบไม่ได้ทันที ข้อมูลเก็บไว้ 90 วัน (admin ดู/กู้คืนได้ที่ `/admin/deleted-users` ทุกการเปิดดูถูกบันทึกใน `AuditLog`) แล้วงานรายวันจะลบชื่อ อีเมล ไฟล์ และข้อความส่วนตัวถาวร (เก็บเฉพาะตัวเลขสถิติ) เจ้าของบัญชีลบเองได้จากหน้าโปรไฟล์
- หน้าเว็บส่ง Content-Security-Policy (นิยามใน `backend/src/config/csp.js` และคัดลอกไว้ใน `deploy/nginx/security-headers.conf`, `frontend/vercel.json` — มีเทสต์ตรวจว่าตรงกัน) ฟอนต์โหลดจากเซิร์ฟเวอร์เราเอง ไม่ส่งข้อมูลผู้เยี่ยมชมให้ Google Fonts
- รูปที่อัปโหลดถูกประมวลผลใหม่เพื่อลบข้อมูลซ่อน (EXIF/GPS)
- ไม่มีโหมดทดลองสำหรับอีเมลแล้ว: ต้องตั้ง SMTP_HOST/SMTP_USER/SMTP_PASS ใน backend/.env (ดูตัวอย่างใน .env.example) มิฉะนั้นการขอ OTP และคำเชิญจะตอบ 503 อีเมลทุกฉบับมีส่วนท้ายระบุแหล่งที่มาและหน่วยงานที่รับผิดชอบ
- รหัสผ่านของคำขอสมัครที่รอ OTP ถูก hash ก่อนบันทึก คำขอเก่าที่ไม่มี hash ต้องขอ OTP ใหม่
- รูปโปรไฟล์ยังเป็น public; เรซูเม่ เกียรติบัตร และเอกสารสมัครงานต้องเข้าสู่ระบบและผ่านการตรวจสิทธิ์
- นายจ้างที่ยืนยันแล้วเข้าถึงเอกสารได้เฉพาะผู้สมัครในงานของตนเอง; admin มีสิทธิ์จัดการเอกสาร
- คอมเมนต์ในชุมชนและข้อความครอบครัวผ่านตัวกรองคำหยาบก่อนบันทึก (`backend/src/services/profanityService.js`) ทำงาน 2 ชั้น: (1) คลังคำไทย/อังกฤษที่รันบนเซิร์ฟเวอร์เราเสมอ จับการเลี่ยงคำแบบเว้นวรรค (`ค ว ย`) ใส่จุด พิมพ์ตัวซ้ำ ตัดวรรณยุกต์ และตัวอักษรล่องหน โดยมีรายการคำยกเว้น (เช่น หีบ, เหี่ยว, โหดเหี้ยม, สัดส่วน) แก้ที่ `BAD_WORDS` / `ALLOW_WORDS` (2) API ตรวจจากบริบท เปิดโดยตั้ง `MODERATION_PROVIDER=openai` หรือ `iapp` พร้อม key ใน `backend/.env` (ดู `.env.example`) ถ้า API ล่มหรือช้าเกิน 3 วินาทีจะใช้ผลชั้นคลังคำแทน
  - ข้อความที่ไม่ผ่านตอบ 400 พร้อมข้อความภาษาไทย และข้อความที่พิมพ์ค้างอยู่ในช่อง ไม่ต้องพิมพ์ใหม่
  - ไม่กรองแชทกับผู้ให้คำปรึกษาโดยตั้งใจ ผู้ใช้ต้องระบายได้ตรงๆ และผู้ให้คำปรึกษาต้องเห็นข้อความจริงเพื่อประเมินความเสี่ยง และไม่กรองโพสต์ของเจ้าหน้าที่
  - ชั้น API มีผลกับ PDPA: เมื่อเปิด ข้อความจะถูกส่งไปยังผู้ให้บริการภายนอก (ข้อความครอบครัวอาจมีข้อมูลสุขภาพ) ถ้าไม่ตั้ง `MODERATION_PROVIDER` ข้อความทั้งหมดอยู่บนเซิร์ฟเวอร์เรา ชั้น OpenAI บล็อกเฉพาะหมวด harassment, hate, sexual — ไม่บล็อก self-harm และ violence เพราะผู้ฟื้นฟูต้องพูดเรื่องเหล่านี้ได้อย่างตรงไปตรงมา
  - ข้อจำกัด: คลังคำไม่รู้จักคำที่ถูกแบ่งครึ่ง (`ค วย`), คำที่ปิดด้วยดอกจัน (`ค**ย`) หรืออักษรหน้าตาเหมือนจากภาษาอื่น และการจับคำสั้นอาจพลาด/เกินในคำที่ไม่อยู่ในรายการยกเว้น จึงมีชั้น API เสริม
- Socket.IO ตรวจ token และเลือกห้องจากตัวตนที่เซิร์ฟเวอร์ยืนยัน ไม่รับรหัสห้องจาก client
- ผู้รับคำเชิญครอบครัวต้องใช้บัญชีครอบครัว/ผู้ดูแลที่อีเมลตรงกับคำเชิญ (ยังรองรับบัญชีผู้ใช้งานเดิม) การสมัครไม่เชื่อมข้อมูลให้อัตโนมัติ ต้องยืนยันลิงก์คำเชิญก่อน หน้าหลักครอบครัวอยู่ที่ `/family/dashboard`

## คะแนนและการแบ่งหน้า

เปอร์เซ็นต์ทักษะตรงกับงาน = จำนวนทักษะที่ผู้ใช้มีและตรงกับงาน / จำนวนทักษะที่งานระบุ
พร้อมแสดงชื่อทักษะที่ตรงกัน หากงานไม่ระบุทักษะจะแสดงว่ายังไม่ระบุ แทนการสร้างคะแนนขึ้นมา
คะแนนนี้ไม่ได้ใช้ข้อมูลสุขภาพ และไม่ใช่โมเดล AI; การประเมินความเสี่ยงยังใช้สูตรตามเกณฑ์ในโค้ด

หน้าค้นหางานของผู้หางานที่ล็อกอินเรียงจากงานที่ทักษะตรงมากไปน้อย (`GET /api/jobs/matched` รับพารามิเตอร์ตัวกรองและ `page`/`limit` เหมือน `/api/jobs`)
เรียงทั้งชุดที่ผ่านตัวกรองก่อนแบ่งหน้า เพื่อให้งานที่ตรงมากไม่ตกไปอยู่หน้าหลัง เท่ากันให้งานที่ตรงจำนวนข้อมากกว่าก่อน แล้วดูงานที่ประกาศใหม่กว่า งานที่ไม่ระบุทักษะอยู่ท้ายสุด
ผู้เยี่ยมชมและบทบาทอื่นยังได้รายการเรียงตามวันที่ประกาศจาก `/api/jobs` เหมือนเดิม

รายละเอียดงานเป็นข้อความอิสระ แต่หน้าเว็บแยกเป็นหัวข้อให้อ่านง่ายเมื่อนายจ้างพิมพ์หัวข้อลงท้ายด้วย `:` แล้วขึ้นต้นแต่ละข้อด้วย `-` (ตัวแยกอยู่ที่ `frontend/src/utils/jobDescription.js`):
`หน้าที่หลัก:` แสดงเป็นรายการหน้าที่ · `คุณสมบัติและสิ่งที่ต้องทำได้:` แสดงเป็นรายการสิ่งที่ผู้สมัครต้องทำได้ · `สวัสดิการและเงื่อนไข:` แสดงเป็นรายการสวัสดิการ/เวลาทำงาน
บรรทัดที่ไม่ใช่หัวข้อหรือรายการจะเป็นย่อหน้า "เกี่ยวกับงานนี้" และประกาศรุ่นเก่าที่มีแต่ `- ...` ยังแสดงเป็นหน้าที่หลักเหมือนเดิม ลิงก์ "ดูประกาศต้นฉบับ" แสดงเฉพาะงานที่นายจ้างใส่ `externalUrl` จริง

`GET /api/jobs?page=1&limit=10` คืน array เช่นเดิม พร้อม `X-Total-Count` ใน response header จำกัดไม่เกิน 50 รายการต่อหน้า
เมื่อไม่ส่ง page จะคงรูปแบบเดิมสำหรับผู้เรียกที่มีอยู่ รายการอื่นแบ่งหน้าฝั่ง frontend

## ตรวจสอบ

```sh
npm test --prefix backend
npm run lint --prefix frontend
npm run build --prefix frontend
npm test --prefix frontend
```

Backend tests ส่วนใหญ่ใช้ model doubles และ configuration สำหรับทดสอบ ไม่ส่งอีเมลจริง ยกเว้น `test/account-lifecycle.integration.test.js`
ที่เชื่อม MongoDB ในเครื่อง (`mongodb://127.0.0.1:27017`, ใช้ฐานข้อมูลชั่วคราวแล้วลบทิ้ง) เพื่อทดสอบการลบ/กู้คืน/ทำให้ไม่ระบุตัวตนของบัญชีกับ MongoDB จริง
หากไม่มี MongoDB เทสต์ชุดนี้จะถูกข้าม (CI เปิด MongoDB ให้)
Browser tests ใช้ API fixtures เพื่อตรวจทุกบทบาทบน desktop, mobile และ dark mode รวม error/retry และ pagination
บน Windows ใช้ Chrome ที่ติดตั้งในเครื่อง; บนระบบอื่นติดตั้ง Chromium ด้วย `npx playwright install chromium` ในโฟลเดอร์ frontend
ผลภาพและ trace อยู่ใน `frontend/test-results/`

GitHub Actions รัน `npm audit` (ช่องโหว่ระดับสูงขึ้นไปทำให้ build ล้ม), backend tests (พร้อม MongoDB), lint, build และ browser tests ทุก push / pull request
และมี CodeQL กับ Dependabot ตรวจโค้ดและ dependency (ดู `SECURITY.md`)
การทดสอบเหล่านี้ยังไม่แทนการทดสอบกับ MongoDB, SMTP และ Google OAuth ที่ตั้งค่าจริง

## ก่อนอัปเกรดระบบที่มีข้อมูลอยู่

การอัปเกรดด้านความปลอดภัยรอบล่าสุด (ไม่มี migration ข้อมูล): ให้ตรวจก่อน deploy
- `backend/.env`/ตัวแปรบนเซิร์ฟเวอร์: ตั้ง `NODE_ENV` ให้ถูก (production บนเซิร์ฟเวอร์, development ในเครื่อง), `JWT_SECRET` ต้องสุ่มยาว ≥ 32, ต้องมี `CORS_ORIGIN` และ `FRONTEND_URL`
  เปลี่ยน `JWT_SECRET` จะทำให้ทุกคนต้องล็อกอินใหม่ (ควรทำถ้าเคยใช้ค่าสั้นหรือค่าตัวอย่าง)
- เซิร์ฟเวอร์ nginx: คัดลอก `deploy/nginx/security-headers.conf` ไปที่ `/etc/nginx/snippets/glow-up-security-headers.conf` ก่อน reload (ดู `deploy/DEPLOY.md`)
- ถ้ามีบัญชีที่สมัครด้วยอีเมลที่เคยมี `+tag`/จุดต่างกัน อาจมีบัญชีซ้ำของคนเดียวกัน (Google กับรหัสผ่าน) ตรวจรายชื่อที่ซ้ำก่อนใช้งาน
- การลบบัญชีเปลี่ยนเป็น soft delete: บัญชีที่ลบไปก่อนอัปเกรดถูกลบถาวรแล้ว ไม่มีรายการให้กู้คืน

มี unique index ใหม่บน `Application(user, job)` เพื่อกันสมัครซ้ำจากคำขอพร้อมกัน
ตรวจและจัดการคู่ user/job ที่ซ้ำในฐานข้อมูลเดิมก่อนสร้าง index โดยสำรองข้อมูลก่อนเสมอ
ไฟล์เดิมยังใช้ URL เดิมได้ แต่เอกสารส่วนตัวต้องมี session ที่ได้รับสิทธิ์
